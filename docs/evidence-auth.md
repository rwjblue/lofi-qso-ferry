# Authentication implementation evidence

Checked 2026-10-22. The implementation pins SimpleWebAuthn server 14.0.3 and browser 14.0.0. [The server documentation](https://simplewebauthn.dev/docs/packages/server), [custom challenge callbacks](https://simplewebauthn.dev/docs/advanced/server/custom-challenges), and the [WebAuthn relying-party requirements](https://www.w3.org/TR/webauthn-3/#sctn-rp-operations) informed the implementation. Library runtime declarations were checked against the installed packages rather than an older example API.

Email signup creates a browser-bound proof with a keyed code digest, ten-minute expiry, five attempts, replaced-code invalidation, and source/address rate limits. Email local-part case and tags remain unchanged; only the domain is canonicalized. The original browser must complete the proof. A confirmed inbox never creates a session. Existing-account proofs direct the owner to passkey sign-in and cannot register a replacement key.

Registration requests discoverable credentials, user verification, ordinary presence, and no attestation. Sign-in challenges have no credential allowlist. Fixed configured RP ID/origin, required UV, matching opaque user handles, active account/key status, and real cryptographic verification establish the tenant. Both registration and authentication explicitly reject cross-origin iframe client data: the installed library deliberately permits some Safari cross-origin assertions without a top-origin value, which is broader than Ferry's policy. Only P-256 ES256 and RSA RS256 credential algorithms are requested and accepted in this initial compatibility profile.

D1 migration `0002_auth.sql` adds transition guards that consume a ceremony and commit its account/key/session change in one transactional batch. A concurrent request cannot win the single-use guard twice. Independent unexpired WebAuthn option challenges remain valid individually, so delayed conditional-autofill options cannot invalidate an explicit sign-in challenge. Replaced email codes are still invalidated. Counter compare-and-set handles concurrent authentication; legitimate zero counters from synced passkeys remain valid. Failed verification consumes the bound ceremony and requires a new action. Adding/revoking keys and changing email require a recent assertion for the same account; a database trigger prevents concurrent revocation of every usable key. Revoking a credential invalidates its sessions.

Sessions use random tokens with only hashes stored, a thirty-day absolute expiry, rotation at login, and Secure/HttpOnly/SameSite=Lax `__Host-` cookies. Every mutation requires the exact configured Origin, JSON content type, and a browser/session-bound CSRF HMAC returned by `GET /api/auth/session`. The server validates session, account, and passkey revocation on every request. Session management supports listing, selected revocation, logout, and signing out other sessions. `purgeAuth()` removes expired mailbox/proof/ceremony/rate/session state; the scheduler must call it. Private keys for passkeys never enter Ferry.

## Email provider and local path

Production email uses [Resend's fixed send endpoint](https://resend.com/docs/api-reference/emails/send-email), an idempotency key per proof, plain-text messages, and a Worker Secret API key. Network redirects are rejected. Failures invalidate the pending proof and return a generic delivery error. Resend delivery itself has not been exercised; configure a verified sender and `RESEND_API_KEY`, and confirm delivery before rollout. Use independent random `AUTH_SECRET` and `EMAIL_CODE_SECRET` bindings; the latter authenticates codes and address rate-limit identifiers.

Local development with `ENVIRONMENT=local`, configured origin `http://localhost:8787`, and the actual request origin matching it uses an encrypted fixture mailbox. `GET /api/auth/local-mailbox` exposes only unexpired messages bound to that browser's secure cookie. It still requires entering the code and completing a real passkey ceremony. Staging/production have no fixture-mailbox response and no email-login/reset bypass. The local mailbox envelope uses the configured KEK and exists only as a reproducible delivery substitute.

## Verified and remaining

`npx tsx --test tests/auth.test.ts` runs generated P-256 authenticators through actual SimpleWebAuthn verification and D1 in workerd. The authenticator signs real client-data/authenticator-data bytes, encodes a COSE public key and none-attestation CBOR, models backed-up synced passkeys with zero counters, and submits concurrent finishes. These tests cover wrong challenge/origin/RP/UV/user handle, wrong purpose and browser, expired/replayed challenges, code attempts/expiry, CSRF, no inbox reset, two isolated accounts, fresh assertions, additional keys, last-key protection, email changes, and session revocation. No verifier is mocked.

The module-level tests execute the library in Node with real D1 in workerd. `npx tsx --test tests/worker-e2e.test.ts` additionally bundles the actual `src/index.ts` Worker, applies all migrations, and completes HTTP email proof, registration, login, dashboard, settings and template flows with the same synthetic authenticator. Real SimpleWebAuthn verification executes inside workerd; no verifier or authentication endpoint is mocked. The static ASSETS service is a fixture returning the actual HTML and bundled browser JavaScript, so these tests do not establish browser rendering. The first passing combined run measured a 1,443,929-byte unminified application bundle; this is evidence about the local artifact, not deployed startup/CPU. The test also verifies two tenants, concurrent login, required UV, no template-triggered ledger work, and disabled production exports with zero vendor/email requests. Synthetic authenticator success is not proof of a hardware/provider/browser combination. A synced 1Password credential, phone/platform passkey, independent security key, mobile browsers, explicit sign-in and conditional autofill need a real browser matrix at the permanent production hostname. There is no automatic recovery if all registered passkeys and provider recovery are lost; the setup/dashboard must state that boundary.
