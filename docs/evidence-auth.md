# Authentication implementation evidence

Checked 2026-10-22. The implementation pins SimpleWebAuthn server 14.0.3 and browser 14.0.0. [The server documentation](https://simplewebauthn.dev/docs/packages/server), [custom challenge callbacks](https://simplewebauthn.dev/docs/advanced/server/custom-challenges), and the [WebAuthn relying-party requirements](https://www.w3.org/TR/webauthn-3/#sctn-rp-operations) informed the implementation. Library runtime declarations were checked against the installed packages rather than an older example API.

Email signup creates a browser-bound proof with a keyed code digest, ten-minute expiry, five attempts, replaced-code invalidation, and source/address rate limits. Email local-part case and tags remain unchanged; only the domain is canonicalized. The original browser must complete the proof. A confirmed inbox never creates a session. Existing-account proofs direct the owner to passkey sign-in and cannot register a replacement key.

Registration requests discoverable credentials, user verification, ordinary presence, and no attestation. Sign-in challenges have no credential allowlist. Fixed configured RP ID/origin, required UV, matching opaque user handles, active account/key status, and real cryptographic verification establish the tenant. Both registration and authentication explicitly reject cross-origin iframe client data: the installed library deliberately permits some Safari cross-origin assertions without a top-origin value, which is broader than Ferry's policy. Only P-256 ES256 and RSA RS256 credential algorithms are requested and accepted in this initial compatibility profile.

D1 migration `0002_auth.sql` adds transition guards that consume a ceremony and commit its account/key/session change in one transactional batch. A concurrent request cannot win the single-use guard twice. Independent unexpired WebAuthn option challenges remain valid individually, so delayed conditional-autofill options cannot invalidate an explicit sign-in challenge. Replaced email codes are still invalidated. Counter compare-and-set handles concurrent authentication; legitimate zero counters from synced passkeys remain valid. Failed verification consumes the bound ceremony and requires a new action. Adding/revoking keys and changing email require a recent assertion for the same account; a database trigger prevents concurrent revocation of every usable key. Revoking a credential invalidates its sessions.

Sessions use random tokens with only hashes stored, a thirty-day absolute expiry, rotation at login, and Secure/HttpOnly/SameSite=Lax `__Host-` cookies. Every mutation requires the exact configured Origin, JSON content type, and a browser/session-bound CSRF HMAC returned by `GET /api/auth/session`. The server validates session, account, and passkey revocation on every request. Session management supports listing, selected revocation, logout, and signing out other sessions. `purgeAuth()` removes expired mailbox/proof/ceremony/rate/session state; the scheduler must call it. Private keys for passkeys never enter Ferry.

## Email provider and local path

Production prefers the native [Cloudflare Email Sending Workers binding](https://developers.cloudflare.com/email-service/configuration/send-bindings/), with both branded HTML/plain-text verification messages and a sender allowlist. An uncertain native failure invalidates the pending proof and returns a generic error; it never sends a second copy through another provider. If no native binding is configured, deployments may use [Resend's fixed send endpoint](https://resend.com/docs/api-reference/emails/send-email), a per-proof idempotency key, and a Worker Secret API key. Redirects are rejected. The selected target requires no Resend API key. Independent `AUTH_SECRET` and `EMAIL_CODE_SECRET` bindings protect sessions and email proofs; the latter authenticates codes and address rate-limit identifiers.

On 2026-10-22 the operator selected origin `https://ferry.n1rwj.com` and RP ID `ferry.n1rwj.com`. Its production `EMAIL` binding is restricted to `signup@ferry.n1rwj.com`. Dedicated Cloudflare sending domain `e69af8ef82a140b38eeaef98d417ef30` was enabled, and `preview_enabled=false` was read back so verification codes are not copied into activity-log message previews. Cloudflare and Google DNS-over-HTTPS independently resolved the sending domain's MX/SPF, DKIM and DMARC records while the parent domain's Fastmail MX records remained unchanged. The production application was subsequently deployed and its live signup form delivered one message to the owner’s Fastmail inbox; only sender, subject and receipt-time metadata were inspected. Production session and discoverable passkey options returned successfully with the exact RP and required user verification, and the local mailbox endpoint returned 404. No account or passkey was created during the smoke test. Personal passkey enrollment at that origin remains for the owner. See [deployment evidence](deployment.md). [Operations](operations.md) records the provisioned database, application secrets and protected backup boundary.

Local development with `ENVIRONMENT=local`, configured origin `http://localhost:8787`, and the actual request origin matching it uses an encrypted fixture mailbox. `GET /api/auth/local-mailbox` exposes only unexpired messages bound to that browser's secure cookie. It still requires entering the code and completing a real passkey ceremony. Staging/production have no fixture-mailbox response and no email-login/reset bypass. The local mailbox envelope uses the configured KEK and exists only as a reproducible delivery substitute.

## Invite-only enrollment and email UX follow-up

Hosted enrollment now requires a seven-day exact-email invitation. The operator task `mise run invite -- person@example.com` grants it in the dedicated D1 before submitting a normal `/join` invitation through Wrangler's native Email Sending command. The link is not a bearer credential. D1 guards claim the invitation in the same account/passkey/session transaction; expiry between the application read and batch rolls the whole activation back. Tests cover uninvited, expired, already-claimed and wrong-case addresses, no mail/proof creation on denial, active invitations after uncertain delivery, operator SQL quoting and refusal to invite existing accounts, plus restore removal. Existing passkey sign-in and authenticated email changes require no new invitation.

Verification messages show a six-digit code in the subject and readable HTML, include a plain-text alternative and expire after ten minutes. Both confirmation fields use one-time-code autofill hints, numeric keyboards, focus and formatted-paste support. The final domain-bound line comes exclusively from the configured origin. Apple's [primary format documentation](https://developer.apple.com/documentation/security/enabling-autofill-for-domain-bound-sms-codes) explicitly describes SMS; email-client autofill remains device-dependent and unverified. Synthetic Chromium desktop/mobile rendering established no overflow or external resources; it is not a live mail-client check.

The actual bundled hosted Worker test completes invited email confirmation, cryptographic passkey registration and zero-connection settings/default-template saving in workerd with D1. A fixed intercepted Resend response exercises production email HTTP without contacting a real provider. This caught Workers rejecting `redirect: 'error'`; the fixed path uses `manual` and rejects non-success statuses, matching [Cloudflare's runtime request options](https://developers.cloudflare.com/workers/runtime-apis/request/#options). A real local Wrangler/Chromium flow independently completed signup with a virtual resident/UV passkey, saved quiet period 40 and a comment default with zero connections, then verified persistence after reload. `/join` stays at its own URL by fetching the root asset internally; fetching `/index.html` had triggered Cloudflare asset canonicalization.

## LoFi connection freshness regression

A deployed LoFi approval attempt exposed a UI gap: a session can remain signed in for 30 days while its security-sensitive action verification expires after five minutes. The browser had ignored the session's `recent` field. Read-only production metadata confirmed an active session beyond that window and no pending LoFi connection; no credentials or source records were read for that diagnosis. The connection handler also flattened vendor HTTP errors into the same misleading passkey/same-origin wording.

Protected browser actions now refresh session/CSRF state, obtain a real passkey assertion when stale, retain the original form payload and continue once. Only an explicit pre-dispatch `reauth_required` code allows a single bounded retry. Typed auth failures are distinct from scrubbed vendor and post-request database failures. Requests pin their original account and CSRF snapshot across preflight/retry; deterministic deferred-response regressions cover another-tab account switches. CSRF/origin, cancellation and ambiguous failures never replay a vendor mutation.

An isolated actual Worker/D1 + Chromium virtual resident/UV passkey regression exercises stale and fresh LoFi approval clicks, cancellation and retry, bad CSRF and throttling. Native `navigator.credentials.get` retained active user activation. Successful clicks each issued exactly one fixture client registration and approval request; cancellation issued none and retained the email/button state. All vendor traffic was contained by an outbound service; there was no real Ham2K mail, vendor export, attempt or outbox write. Physical/synced passkeys and actual owner approval remain personal verification.
