# Direct LoTW signing evidence

Checked 2026-10-22. This is local compatibility evidence, not ARRL acceptance.

The Worker imports legacy RC2/3DES and current PBES2/AES PKCS#12 files, verifies their integrity MAC, requires exactly one matching RSA key/certificate, extracts LoTW callsign/DXCC and separate QSO authorization dates, then normalizes to PKCS#8. Import is bounded at 256 KiB, eight certificates, 100,000 KDF iterations, 12,000 decoded nodes and 32 inspected levels. Unknown trust/revocation remains explicit; signing requires a configured trusted chain and an unrevoked status checked within 24 hours. Passwords and original PKCS#12 bytes are not part of normalized credentials.

The signing profile is `ferry-lotw-v2-us-ca-1`. US and Canadian subdivisions and a conservative explicit mode/band set are supported. SSB with USB/LSB ADIF submodes uses the supported SSB parent mapping, while FT4 remains exact. Other subdivision schemes, unknown modes and satellite names not yet accepted by ARRL require configuration evidence before rollout; values are never silently dropped or mapped to DATA. US county syntax is checked, but the full current ARRL county enumeration still requires rollout validation. Mixed callsigns, DXCC or locations must be separate artifacts. Each artifact carries exact source UUID/generation members, credential version and configuration version. The coordinator durably encrypts it before dispatch. The adapter limits an artifact to 100 contacts; initial orchestration can use one contact.

The field order and legacy RSA SHA-1 wire signature were compared with [Wavelog's pinned direct signer](https://github.com/wavelog/wavelog/blob/7f8eef4de94c674f73c6859ed4e0b0247f68dcd9/application/views/lotw_views/adif_views/adif_export.php) and [certificate import/status handling](https://github.com/wavelog/wavelog/blob/7f8eef4de94c674f73c6859ed4e0b0247f68dcd9/application/controllers/Lotw.php). Adapted ordering retains its MIT notice in `fixtures/signing/WAVELOG-LICENSE.txt`. Application hashes remain SHA-256. `fixtures/signing/vector.json` has exact canonical bytes and an independent `openssl dgst -sha1` signature using the explicitly synthetic private key. No personal key or contact was used.

## Runtime experiment

Run `npx tsx --test tests/signing.test.ts tests/lotw.test.ts tests/signing-runtime.test.ts`.

The actual local workerd process (Miniflare, compatibility 2026-10-22, `nodejs_compat`) successfully imported both fixtures, verified chain signatures with WebCrypto, imported PKCS#8, generated byte-identical RSA/SHA-1 signatures, and produced gzip artifacts. The final run on pinned Node 24.21.0 measured approximately 362 ms wall time for cold dispatch plus two imports and two one-contact signatures; each synthetic compressed artifact was 1,526 bytes. Tests print current measurements.

The integrated Worker also passed `npx wrangler check startup --env=`. Wrangler reported 1,534.84 KiB raw and 290.24 KiB gzip for the complete bundle. Its local startup profile covered a 80.4 ms window, with 73.4 ms sampled: 49.1 ms active (including 0.0 ms garbage collection), 24.3 ms idle and 29 samples. These are local profile observations, **not deployed billed CPU, peak-memory measurements or LoTW acceptance evidence**. Worker clocks stop during synchronous code; wall time and sampled startup activity cannot substitute for deployed import/batch resource measurements. Deployed Worker CPU/peak-memory and larger representative batch measurements remain required before enabling production writes.

`node-forge@1.4.0` has [GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv), with no fixed published version at investigation time. Production code never uses Forge RSA/certificate signature verification. It verifies exact DER certificate TBS bytes with strict platform WebCrypto instead. A focused regression constructs the nested DigestAlgorithm garbage accepted by Forge and proves that the production verifier rejects it. Forge is used for ASN.1/PKCS#12 MAC/decryption and key extraction; dependency updates still require review. Trusted roots come from deployment configuration, never imported PKCS#12 trust claims.

## Submission and readback

[ARRL submission documentation](https://lotw.arrl.org/lotw-help/developer-submit-qsos/) defines signed uploads and `.UPL.` accepted/rejected comments. The real adapter sends gzip TQ8 as multipart `upfile` to the fixed HTTPS upload endpoint. It reports queue acknowledgement as `submitted`; missing responses, transport errors, redirects and unexpected responses remain `uncertain` and cannot authorize blind retry. Both the deployment export gate and explicit live-write authorization must pass before dispatch.

[ARRL query documentation](https://lotw.arrl.org/lotw-help/developer-query-qsos-qsls/) defines accepted unconfirmed records, own-station detail, receive-time watermarks, and the current EOF marker. Query uses `qso_qsl=no`, explicit `qso_qsorxsince`, `qso_withown=yes` and `qso_mydetail=yes`. It streams at most 2 MiB per inclusive 32-day partition; overflow, HTML, missing EOH/EOF, inconsistent NUMREC, malformed identities or truncation cannot establish coverage or absence. Callers must split and complete larger query scopes; v1 orchestration uses a single contact’s UTC day and station/worked-call filters, and parks oversized responses rather than claiming absence. A receive checkpoint applies only to the identical query, and resumption should overlap the inclusive timestamp boundary.

Readback frequency has five decimal MHz places (10 Hz); finer transmitted precision is explicitly `insufficient_evidence`, so an old rounded record cannot acknowledge a one-Hz correction. Observation requires exact seconds, unique identity and the supported readback-visible station/contact projection. Minute-only records are ambiguous. Accepted/unconfirmed and confirmed remain separate; seeing an older identity with the wrong location/frequency does not acknowledge a correction. County readback is compared with ADIF `state,county` representation. This representation and legacy/current live certificate formats still need scoped vendor readback evidence.

## Remaining live inputs and checks

- Configure and independently verify the LoTW issuing/root certificate trust bundle. A certificate-only `.tq6` is insufficient; signing requires a matching `.p12` private key.
- Import the owner's LoTW `.p12` through a freshly passkey-verified session. The original password is used only for import. Confirm the status endpoint and issuer chain with that certificate, and verify supersession/revocation behavior.
- Optional LoTW website username/password allow full accepted-history adoption and uncertain-result readback. Without them prior history stays unverified.
- Deploy the disabled-export Worker, measure billed CPU/memory for import and representative signing batches, and compare a designated synthetic/reference signing vector with native TQSL if available.
- Obtain explicit authorization for one identifiable genuinely new QSO; upload it, observe its exact supported projection at LoTW, separately record confirmation, and record revision/credential/configuration versions before expanding.

The synthetic signing experiments made no live certificate import or upload. A later scoped live read-only LoTW query is recorded in [live read-only evidence](evidence-live-readonly.md); it does not prove signed-upload acceptance. No production compatibility claim follows from fixture success.

## Connection and account identity

The connection API stores `{signingCredentials: [...], query?: {username,password}}` only inside the encrypted credential envelope. A verified LoTW website query username establishes a stable `query:<username>` logical destination. Subsequent imports for that same query account merge certificates by exact callsign/DXCC, replacing a renewed pair in the active credential version and preserving the destination ledger. Current v1 limits each account to eight station certificates. The original certificate versions remain available for immutable in-flight attempts until bounded retention expires; revoked connections delete credential ciphertext immediately and cancel unsent work.

Without query credentials, a certificate cannot establish LoTW website account identity. The connection therefore uses a distinct `station:<CALL>:<DXCC>` destination. Adding verified query credentials creates a separate logical destination and requires read-only reconciliation; it cannot silently inherit unverified station mappings. Different active routes that overlap a callsign/DXCC must be blocked as ambiguous by orchestration. Certificate imports alone perform no QSO signing or submission. `needs_verification` imports remain inactive until trusted roots and status evidence are resolved.

Connection tests exercise two synthetic certificates on one verified query account, renewal without destination replacement, no-write LoFi/QRZ verification, session freshness/CSRF, cross-tenant requests, credential encryption, revocation, and transaction guards that reject a session revoked during a vendor read. The fixture tests do not establish live account access. Later bounded read-only checks verified QRZ STATUS field names and existing LoTW query access; see [live read evidence](evidence-live-readonly.md).
