## Deployed read-only target

The selected production origin/RP is `https://ferry.n1rwj.com` / `ferry.n1rwj.com`. Worker `lofi-qso-ferry` is deployed read-only with its secrets provisioned; dedicated D1 `ferry-production` has all six migrations applied. The native Cloudflare `EMAIL` binding is restricted to `signup@ferry.n1rwj.com`, with sending DNS verified and message preview disabled. No Resend key is needed. Three independent application secrets have a protected local backup; transfer to the operator's secret manager remains pending because 1Password CLI was signed out. Production `workers.dev` and preview URLs are disabled; staging remains an undeployed placeholder. All five export gates remain closed. See [operations](operations.md) for resource IDs and backup details; [deployment evidence](deployment.md) records the actual version, HTTPS/gate checks and signup-message delivery. Hosted enrollment is now invite only through the operator task; existing users keep their passkeys. Actual local Worker/browser verification covers enrollment and settings with zero service connections. Physical/synced-device and mail-client autofill checks remain personal acceptance work.

## Inputs required to resume

1. **Secret backup:** preserve the provisioned production keys and complete their secure secret-manager backup; the application deployment and HTTPS/disabled-health checks are complete. No new hostname, D1 resource or Resend key is required for this target. Follow [operations](operations.md); do not paste secrets into issues or commits.
2. **Source boundary evidence:** complete read-only LoFi inventory and server replay/tombstone guarantees or controlled experiments sufficient to establish them. Record server cursor evidence and aggregate counts, never device-clock substitutes. Until then `SOURCE_BOUNDARY_VERIFIED=false`; no missing-history export or no-query live cutover is authorized.
3. **Signing inputs:** an authorized LoTW PKCS#12 certificate/private key and import password, authoritative trust certificates, current certificate status, station callsign/DXCC/QSO-date coverage and supported station locations. Optional LoTW query credentials enable adoption and result reconciliation. An unknown trust root is never activated merely because import succeeded.
4. **Scoped vendor writes:** explicit authorization naming the QRZ test book, LoTW account and exact synthetic/new contact UUIDs. Verify mutation, duplicate, replacement, lost-response, confirmed-record, portable-location and ARRL acceptance behavior without rewriting existing history. QRZ old-identity cleanup remains disabled until separately proven safe.
5. **Account/browser verification:** start a fresh signup in the owner’s browser, confirm its email, enroll two independent passkeys and exercise the documented Safari/Chrome/synced-provider/backup-key matrix. There is no inbox reset or alternate sign-in path.
6. **Owner-history review:** with exports disabled, complete source and both destination read-only reconciliation and inspect aggregate adoption/ambiguity/unverified exceptions. A bounded vendor sample is not this inventory.
7. **Measured deployment:** record revision, bundle/startup, billed CPU/memory, D1 reads/writes/storage, email usage and projected monthly cost on a representative workload. Run restore quarantine and credential revocation checks before expanding coverage.

## Enablement sequence

Deploy with gates closed, finish the read-only and account checks, and record evidence. Authorize only a small identifiable UUID allowlist for the first writes, verify both destinations and their narratives/locations, then explicitly expand coverage. A destination outage must not suspend the other destination.

The Worker requires `EXPORTS_ENABLED=true`, `ROLLOUT_CHECKS_PASSED=true`, `SOURCE_BOUNDARY_VERIFIED=true`, the explicit `LIVE_WRITE_AUTHORIZATION` value documented in [operations](operations.md), and a nonempty `ROLLOUT_QSO_IDS_JSON` allowlist (or an explicitly authorized `["*"]`). Configuration alone cannot establish a vendor contract. Do not set proof gates merely to make a demo submit.

A QRZ upload response can establish its receipt only under the verified contract. A LoTW upload acknowledgment means submitted; exact subsequent readback establishes observed acceptance, and QSL confirmation is independent. Uncertain outcomes require readback and remain visible when no safe conclusion is available.
